# Архитектура

**Статус:** начальный проект. Документ фиксирует границы и инварианты, но не навязывает конкретные имена классов и модулей.

## Цели

Система должна:

- детерминированно объяснять поддерживаемое поведение GitLab CI;
- отделять исходную конфигурацию от эффективной;
- сохранять происхождение значений и решений;
- работать офлайн для локальных возможностей;
- явно показывать неподдерживаемую семантику;
- позволять тестировать ядро без файловой системы, терминала и сети.

## Не входит в цели

Проект не выполняет `script`, не планирует pipeline, не заменяет GitLab Runner и не проверяет произвольные shell-команды. Ранним версиям не нужны сервер, база данных, система плагинов, фоновые процессы и LLM-интеграция.

## Модель обработки

```text
файлы конфигурации + необязательный контекст pipeline
                         │
                         ▼
                  загрузка источников
                         │
                         ▼
                     разбор YAML
                         │
                         ▼
                 сборка конфигурации      появляется на этапе 2
                         │
                         ▼
              семантическая нормализация
                         │
                         ▼
                 вычисление контекста     появляется на этапе 3
                         │
                         ▼
            модель фактов и объяснений
                         │
                         ▼
             текстовый или структурный вывод
```

На этапе 1 реализуется только минимально полезный путь: загрузить файл, разобрать YAML, нормализовать job, этапы и `needs`, затем вывести сводку.

## Зоны ответственности

Это логические обязанности, а не обязательные классы Python.

### Загрузка источников

Читает локальный файл и фиксирует его происхождение. Позже здесь появятся локальные `include` и клиент GitLab. Сетевой код не должен проникать в семантическое ядро.

### Разбор YAML

Преобразует YAML в обычные данные и по возможности сохраняет сведения об источнике. Этот слой отвечает на вопрос «что записано», но не вычисляет семантику GitLab CI.

### Сборка конфигурации

Разрешает `include`, наследование, значения по умолчанию и переопределения. Для каждого эффективного значения должен быть известен источник либо документированное правило GitLab.

### Семантическая нормализация

Приводит гибкие формы YAML к небольшому набору понятий: job, скрытые шаблоны, этапы, зависимости, правила, переменные и диагностика. Следующие слои не должны заново интерпретировать все варианты YAML.

### Вычисление

Применяет явный контекст pipeline к `workflow` и правилам выбора job. Результат должен содержать решение и факты, которые к нему привели. Неизвестное и неподдерживаемое выражение отличается от `true` и `false`.

### Объяснение

Хранит факты вроде: «второе правило совпало, потому что `CI_PIPELINE_SOURCE` равно `merge_request_event`». Человекочитаемый текст строится из этих фактов, а не заменяет их.

### Представление

Форматирует результат для человека или программы. Этот слой не вычисляет семантику GitLab CI. Текстовый вывод должен быть детерминированным.

## Инварианты

1. **Никакого молчаливого отката.** Конструкция может быть поддерживаемой, невалидной или неподдерживаемой. Неподдерживаемое нельзя трактовать как отсутствующее.
2. **Явные значения по умолчанию.** Значение из правила GitLab отличается от значения, записанного в YAML.
3. **Происхождение не теряется.** После сборки конфигурации должно быть понятно, где значение появилось и где было переопределено.
4. **Никакого выполнения.** Скрипты и строки конфигурации остаются данными и не исполняются как shell- или Python-код.
5. **Чистая семантика, где это практично.** Файлы, терминал, часы, переменные окружения и HTTP-клиент остаются на границах.
6. **Стабильный порядок.** Вывод не зависит от случайного порядка обхода и параллелизма.
7. **Явная версия совместимости.** Инструмент не заявляет поддержку всех версий GitLab.

## Модель ошибок

Пользовательские ошибки делятся на категории:

- ошибка вызова CLI;
- ошибка источника: файл отсутствует или не читается;
- синтаксическая ошибка YAML;
- семантическая ошибка поддерживаемой конструкции;
- неподдерживаемая возможность GitLab CI;
- внутренняя ошибка инструмента.

Ожидаемая ошибка пользователя не должна печатать traceback. Неожиданный сбой нельзя маскировать под ошибку конфигурации.

## Совместимость

Синтаксис GitLab CI меняется. Каждая реализованная возможность должна опираться на официальную документацию и регрессионные тестовые примеры. Позже репозиторий должен явно указывать целевую версию или диапазон версий GitLab.

Основные источники:

- [синтаксис CI/CD YAML](https://docs.gitlab.com/ci/yaml/);
- [конфигурация `include`](https://docs.gitlab.com/ci/yaml/includes/);
- [зависимости `needs`](https://docs.gitlab.com/ci/yaml/needs/);
- [оптимизация YAML и `extends`](https://docs.gitlab.com/ci/yaml/yaml_optimization/);
- [переменные CI/CD](https://docs.gitlab.com/ci/variables/);
- [CI Lint](https://docs.gitlab.com/ci/yaml/lint/).

Сравнение с GitLab может стать дополнительной проверкой, но реальные вызовы API не должны входить в быстрый обязательный набор тестов.

## Безопасность

Любой файл конфигурации считается недоверенным входом.

- Использовать безопасный загрузчик YAML без создания произвольных объектов.
- Не выполнять `script`, shell-выражения и код, указанный в конфигурации.
- Для локальных `include` ограничить чтение корнем проекта и отдельно обработать выход через `..`, символические ссылки, циклы и повторные файлы.
- Не добавлять удалённую загрузку до проектирования аутентификации, редиректов, лимитов размера, таймаутов и разрешённых протоколов.
- Не выводить токены и секретные значения переменных в диагностике.

## Тестирование

Предпочтительны тесты наблюдаемого поведения:

- небольшие модульные тесты нормализации и вычисления;
- параметризованные сценарии разных форм YAML и границ;
- файловые примеры для сборки конфигурации и происхождения значений;
- интеграционные тесты CLI для вывода и кодов возврата;
- регрессионный тест для каждого подтверждённого дефекта.

Тесты должны защищать поведение и правила предметной области, а не имена внутренних функций и случайное расположение модулей. Внешние тесты GitLab, если появятся, запускаются отдельно и необязательно.

## Политика изменений

Использовать самое простое представление, достаточное для текущего этапа. Новая абстракция появляется только под конкретное поведение. ADR нужен лишь для дорогого в изменении решения, контракта совместимости или изменения ключевого инварианта.
